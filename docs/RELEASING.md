# Releasing AirFlash

Stable releases are built from `main` by the manually dispatched **Release** GitHub Actions workflow. It installs and validates the selected .NET SDK before reserving a version, then runs native/.NET/Python checks, builds fresh Windows x64 binaries, verifies versions and checksums, exercises MSI installation in a disposable runner, and publishes the release only after success.

Desktop tray verification is documented in [TRAY-DIAGNOSTICS.md](TRAY-DIAGNOSTICS.md).

Versions are three numeric components. `reserved/X.Y.Z` tags are permanent reservations, including failed builds. Never remove, move, or reuse them. The pre-GitHub floor is 0.2.3. `vX.Y.Z` identifies a published release and points to its source commit. Concurrent workflow runs are serialized; atomic remote reservations also prevent local collisions.

Development builds use `pwsh scripts/build-dev.ps1`. They derive `X.Y.Z` from the latest local stable `vX.Y.Z` tag, append `-dev.<8-character-commit>` (and `.dirty` when tracked files are modified), and write `dist/dev/AirFlash.exe` plus `dist/dev/AirFlash-X.Y.Z-dev.<commit>.msi`. They do not query the remote, reserve a version, push a tag, or write `artifacts/release-version.txt`. The development MSI uses the current stable numeric ProductVersion for Windows Installer compatibility; uninstall an existing same-version package before installing it.

A production release build must run from clean `main`, with the authenticated `origin` set to `https://github.com/Ding-Kyoma/AirFlash` (optionally ending in `.git`). The production helper deliberately rejects the fork origin. In the original maintainer's release checkout, `pwsh scripts/build-release.ps1` reserves its own increasing version remotely. Preserve `artifacts/release-version.txt`. Local production builds reserve a version even without publication; never pass an old reservation to rebuild a published version. For own-fork builds, use the unreserved preview artifact workflow below and retain the fork's existing remotes.

The workflow's optional `version` input reserves an explicit new version, for example `gh workflow run release.yml --ref main -f version=0.3.0`. Leave it empty to increment automatically. Local release validation builds also accept `pwsh scripts/build-release.ps1 -NewVersion X.Y.Z`. Explicit versions must exceed every remote reservation, published stable version, local version record, existing EXE version, and source baseline, and fit both MSI and assembly limits (255.255.65534). Input must be canonical ASCII X.Y.Z with no surrounding whitespace or line endings. Automatic increments roll from patch 65534 to the next minor version; historical 65535 tags still set the version floor. The standalone installer retains the MSI-only 65535 limit. `-NewVersion` cannot be combined with `-ReservedVersion`; the latter is internal to the Actions job that just reserved the version. Failed builds consume their version. Never retry a failed build with the same explicit version, even on the same commit.

Release verification gives each owned self-check or compatibility process thirty seconds, followed by at most five seconds for settlement. It disposes the owned process, rejects missing/newly malformed reports, removes stale report leaves before launch and preserves the original failure if cleanup also fails. This deadline does not certify or terminate unrelated application or engine processes.

When the release commit modifies workflows, use a maintainer login with workflow-write permission for publication. Dispatch `gh workflow run release.yml --ref main -f version=0.3.0 -f publish=false`. The workflow performs the same build, version, checksum, and installer lifecycle checks, then uploads `airflash-release-<version>-<sha>` without publishing. Download this artifact only from a successful run, verify both file hashes against `SHA256SUMS.txt`, and confirm the run SHA matches `main` and `reserved/<version>`. Publish those exact files with `gh release create v<version> AirFlash.exe AirFlash-X.Y.Z.msi SHA256SUMS.txt --target <verified-sha> --title "AirFlash <version>" --notes-file docs/RELEASE-NOTES.md --latest`. Confirm the release is not a prerelease, is Latest, has all three assets, and its tag points to the verified SHA. The `publish` input defaults to `true`, preserving automatic stable publication. Preview runs always retain their existing artifact-only behavior.

Complete local validation builds before reserving the intended public version, so that the workflow can reserve it as a fresh version.

For local SDK/cache reuse use the checkout's ignored `artifacts` directory or the shared Git integration checkout. `DOTNET_CLI_HOME` and `NUGET_PACKAGES` can override cache locations. Install the .NET 10 SDK, Rust MSVC toolchain and Visual Studio C++ tools before building.

Run `pwsh scripts/check-dotnet.ps1` to check the selected host without starting a release build. Selection prefers the checkout's `artifacts/dotnet/dotnet.exe`, then the integration checkout's equivalent, then `dotnet` on PATH. The selected host resolves `desktop/global.json` from `desktop`, allowing its configured SDK roll-forward. A runtime-only or incompatible preferred installation fails with its path and policy; replace or remove that installation rather than expecting fallback to PATH. `scripts/build-release.ps1` performs this check before the release lock, reservation, output cleanup or native work, and keeps the same selected host for desktop publish and MSI build. `scripts/dotnet.ps1 --info`, `--list-sdks` and `--list-runtimes` remain available without a compatible SDK. Later build failures still consume a reserved version.

Release assets are `AirFlash.exe`, `AirFlash-X.Y.Z.msi`, and `SHA256SUMS.txt`. Validate a downloaded asset with `Get-FileHash -Algorithm SHA256`. The binaries are currently unsigned.

Installer lifecycle tests run only in the disposable GitHub runner. First release tests use a lower-version fixture built from the same source to exercise upgrades; subsequent releases additionally use the preceding public MSI. They do not interact with HomePods.

Local agent instructions, worktree hooks and history backups are deliberately not distributed. They live only in the maintainer's Git common directory and ignored files.

## Own-fork preview artifacts

The fork's **Fork integration validation** workflow can build a runnable preview from an exact Main commit without reserving a version, pushing tags or creating a GitHub Release:

```powershell
gh workflow run fork-integration-validation.yml --repo ThatMarko/AirFlash --ref main -f source_commit=<full-main-commit> -f package_version=6.0.1 -f package_channel=preview -f complete_ui_matrix=true
```

Use the actual full Main SHA in place of the placeholder. The defaults remain the unreserved 0.3.1 validation package in the stable filename format. This `preview` example produces `AirFlash.exe`, `AirFlash-6.0.1-rc.1.msi`, checksums and a source manifest in the successful run's artifact. EXE/assembly/MSI numeric versions are 6.0.1; informational metadata carries the preview suffix and source SHA, and the application displays Preview. Numeric inputs are checked before SDK/dependency/native/package work, including the assembly-version build limit and the installer's lower-predecessor requirement. Artifact retention is fourteen days.

Review history `bbe283c` was merged into fork Main at `f8472e5` without changing the existing Main tree. Reviewed tooling and notice follow-ups subsequently advanced the public branch to `07dd238` and were integrated into Main at `8b94f3b`. The previously delivered 6.0.0-rc.1 preview remains bound to `32b49cb`; these source changes do not replace that binary. The fork validation workflows and all documentation changes stay on fork Main. The build tests fake services and installation only on the disposable runner; downloading its artifact does not install or launch anything on the local computer.

The user-selected 6.0.1-rc.1 example was built and independently qualified from exact Main `8b94f3b` in [run 39697631837](https://github.com/ThatMarko/AirFlash/actions/runs/39697631837). Its verified portable/MSI files were copied into a new `dist/preview-6.0.1-rc.1-8b94f3b` folder, without launching/installing them or replacing the earlier preview. See [audit acceptance](issues/GITHUB-SCRIPTS-ACCEPTANCE-2026-10-21.md) for executed checks and limits; this artifact creates no release or reservation tag.

An ordinary portable launch shares the installed application's profile. Close the running application and preserve the old configuration before a manual comparison: saving migrated schema-4 settings prevents the older schema-2 fork release from loading that configuration. Native credentials and the mute journal have independent per-user locations. Do not restore a journal backup as a configuration rollback. A numeric 6.x MSI also prevents a later lower-numbered MSI upgrade until it is uninstalled; the portable EXE avoids that installer registration change.

## Original-repository NIC-preview release channel

The production scripts retain `codex/nic-discovery-preview` as an allowlisted channel. This section describes its release mechanics, not the current integration state of discovery features. It applies only to the original maintainer's production checkout with the required `Ding-Kyoma/AirFlash` origin; own-fork preview users should use the unreserved workflow above. An authorized production preview dispatch selects **Release** on `codex/nic-discovery-preview`; `main` remains the stable channel. It reserves the next numeric version (including previous preview reservations), runs the same tests, builds and verifies the EXE/MSI, checks installer lifecycle in a disposable runner, and uploads `airflash-preview-<version>-<sha>`. A failed attempt consumes its reserved version; another production attempt requires a new version.

The workflow deliberately does not create a GitHub Release for the preview. The branch changes `.github/workflows/release.yml`, so GitHub's ordinary Actions token cannot create a release targeting that commit without workflow-write permission. The maintainer downloads the verified artifact from the successful run, verifies `SHA256SUMS.txt` against both files, confirms the run SHA matches the current PR head and `reserved/<version>` tag, then publishes with a maintainer `gh` login authorized for workflow changes:

`gh release create v<version>-rc.1 AirFlash.exe AirFlash-X.Y.Z-rc.1.msi SHA256SUMS.txt --target <verified-sha> --title "AirFlash <version> Preview" --notes-file docs/PREVIEW-NOTES.md --prerelease --latest=false`

Verify the resulting release is marked prerelease, is not Latest, has the three assets, and its tag points to the verified SHA. The installed application displays **Preview**; its MSI ProductVersion and EXE file version are numeric `<version>`. The About update check still queries only the latest stable release. After validation, merge the PR and dispatch the stable workflow from `main`; it reserves a *new* higher numeric version. Never repurpose the preview tag or version. Test upgrading the preview MSI to that stable release in a disposable runner.

Preview verification uses `scripts/verify-release.ps1 -Version X.Y.Z -ReleaseChannel preview`; the channel selects the `-rc.1` MSI filename while version checks remain numeric. Stable verification keeps the default channel. Packaging and verification share the artifact-version policy, which also supplies the preview workflow asset path.
